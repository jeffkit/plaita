## 单① #319：父行删除钉观察快照（id + created_at 双条件）

### 缺陷机制（实证收敛，非 B2 注记原文的「PG MVCC 复生」字面）

两主体（create×delete）在快照隔离下「删→建」方向**闭合**：行在时 create 的
存在性预检（读已提交态）必 409、行不在时 delete 必 404——探针
（`/private/tmp/r92_probe_create_delete_race.py`，seam×引擎 8 格 + 自由竞
40 轮）全为合法终态。真正的洞在**删除侧收尾**：

- `delete_flow` 的父行收尾用 `session.delete(record)`——ORM DELETE **只按
  代理主键 id 定位**，且实际 SQL 在 commit 前 flush（`_outbox_purge` 的
  autoflush 处）执行；
- SELECT 观察到提交之间，旧行可被并发删除并由同 id `create_flow` 重建：
  **SQLite rowid 复用**（无 AUTOINCREMENT，max+1）使重建行 id 与观察行相同
  → 收尾 DELETE **命中重建行**（rowcount=1，静默「成功」）；PG/MySQL 序列
  不复用 → 零命中且 `confirm_deleted_rows` 仅 WARNING、**假报删除成功**；
- 终态（负控实录）：create 201 已返回 + delete 200 + 行/版本消失＝「删除
  吞掉刚重建的同名 flow」（create×delete 两面即 B2 r92 残面注记所指；
  「行在但版本/定义不一致」为 PG 形态——重建行幸存而其 flow_id 面版本/定义
  被收尾事务的 flow_id 维度语句吃掉）。
- `expected_versions` 钉版路径（A134-02）挡版本行漂移，但重建期 save 同
  version/status 可穿过钉版 DELETE（rowcount=1），父行收尾仍无任何钉。

### 修法

`delete_flow` 父行收尾改**钉观察快照**的条件 DELETE（`id + created_at` 双
条件，`created_at` 不可变且重建必换值；PG/MySQL 上 created_at 同秒截断无妨
——id 已不复用）+ rowcount 复核：≠1 → `VersionConflictError`（409 语义，
文案「在删除期间被并发修改或重建」）→ 事务整体回滚（本事务已执行的版本行
删除/outbox purge 一并还原）——与 `_delete_versions_pinned`「快照失配 →
具名 409、零删除」同语义收敛。API 既有 `VersionConflictError → 409
version_stale` 处理面零改动。

### 负控（先红后绿，确定性三段交错，零竞态运气）

时序：陈旧删除在首个 `delete()` 构造点停表阻塞（SELECT 已完成、写锁未取）
→ delete#1 完整提交（旧行死亡）→ create 重建提交（SQLite rowid 复用同 id，
负控实测观察行 id=1 → 重建行 id=1）→（钉版格再加同名同状态版本 save）→
放行陈旧删除收尾。

## 单② #335：executions API 手动 start/resume 切 engine backend + 删旧环

### 范围裁量（对 #335 正文的勘误性注记）

#335 正文「删除 local_scheduler 旧环」按 r96 proofs 的阶段边界原文（「API
的手动 start/resume 仍走 **local_executor** 旧环（阶段 3 收口：合并后删第二
套 executor）」）裁量执行：删的是 **local_executor 的第二套执行器驱动**
（`start_local_execution` / `resume_local_execution` / `_run_flow` /
`_load_definition` / `_ThreadLogHandler`，约 330 行）。`local_scheduler`
模块**保留**——其 `fire` 阶段 2 已切 engine backend，扫描循环是本地档调度
的活特性（A48），删之违反「API 调用面零变化」验收。

### 交付

1. `engine_backend.resume_execution`（新宿主入口）：与旧
   `resume_local_execution` 逐项对齐——行缺失 `False` / 非挂起 /
   `continue|retry`（#33）/ checkpoint 缺失均 `ValueError` 同文案；挂起→
   running 原子 CAS 并发互斥；`_spawn` 同 id 线程存活拒绝→回滚状态再拒。
   驱动 = `launch_resume` → `worker.resume_flow`（lease/终态幂等/挂起幂等
   短路/flow_hash 守卫沿用基类；本地行无 flow_hash 列跳过）；
   `_with_resume_binding`（#221）与行上 **nodes 续栽**（恢复不清节点
   trace——缺此即恢复首拍清空重写）同源保留（`build_worker(initial_nodes=)`）。
2. API 两分支切换：`POST /executions`（local 分支 → `start_execution`）、
   `POST /executions/{id}/resume`（local 分支 → `resume_execution`）——
   HTTP 契约（状态码/错误 detail/响应形）零变化。
3. 删旧环 + 文档面：模块 docstring 重写（残面=注册表/控制面/读面/共享装配）；
   `local_scheduler`/`api`/`flow_store` 处误导性引用清理。
4. **`LocalMirror.record_failed` usage 聚合两段兜底**（#37 P2 守恒，负控
   当场抓获）：worker 的 start 失败路径刻意留 running 行（集群 at-least-once
   契约），咽喉点 `_collect_usage` 不经此路 → 行上无 checkpoint。聚合源：
   行上最后持久化 context → trace 回调已落库的节点 `output.usage`
   （`aggregate_node_usage` 同口径，零 schema 变更）。
